Latency and paging measurements, taken on the affected machine
================================================================

What this is
------------
This is not a report produced by LatencyMon. LatencyMon is not installed on this machine, so
instead the same underlying sources were measured directly: the Windows kernel event tracing for
DPC/ISR execution times with per-driver attribution, and the Windows performance counters for
paging.

The DPC/ISR figures below were taken while the fault was active - audible crackle, with the audio
engine logging missed deadlines. The paging figures were sampled afterwards during normal use of
the machine. Nothing here was recorded on an idle or freshly booted system.

For completeness: one other trace
--------------------------------
A separate kernel trace taken on 21 September 2026, during a heavy background disk search, did
record storport.sys DPCs up to 6.8389 ms. That trace was not taken during a fault, and four
bounded read-only disk-load tests performed afterwards did not reproduce the playback fault at
all. The spike is on record, but it is not the trigger.

Verdict
-------
No driver in the audio path shows DPC or ISR execution time large enough to cause this, the audio
engine thread is not being starved of CPU, and there is no hard paging. This is not a latency,
scheduling or memory-pressure problem.

The failure is visible instead in the driver's own trace output: a completed playback request is
never resubmitted, so the ring of ten requests becomes nine, then six, then one; with one request
left the schedule runs about 185 frames behind the USB frame counter and every transfer completes
reporting success while transferring zero bytes of audio.

Raw traces, including the one the DPC/ISR figures come from, are available on request; three of
them are published in the release linked from the repository.
